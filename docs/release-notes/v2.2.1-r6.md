Released: 2026-10-17. Sixth pre-release revision of the v2.2.1 line,
published as a pre-release awaiting maintainer approval. Per the
project's versioning policy (docs/DECISIONS.md), the machine-readable
version fields (package.json, tauri.conf.json, Cargo.toml,

## Headline 1: Word-to-LaTeX now extracts footnote and endnote references

A user reported that the Word-to-LaTeX converter was "only converting 5
references" of their manuscript. An initial external review hypothesized
a hardcoded `.take(5)` cap that **did not exist in the source**. The
actual root cause was more subtle, and the fix closes a real silent-drop
bug that contradicted the README's "never silently dropped" promise.

### What was actually happening

`convert_docx_to_latex` only read `word/document.xml`. Any reference
stored in `word/footnotes.xml` or `word/endnotes.xml` was silently
dropped. This matters because many academic styles store the
bibliography in footnotes:

- **Chicago notes-bibliography** style emits every citation as a Word
  footnote (`References → Insert Footnote`).
- **Vancouver with footnote citations** (some medical journals) does
  the same.
- Any manuscript where the author used Word's "Insert Footnote" for
  reference annotations stores those references in `word/footnotes.xml`,
  not in `word/document.xml`.

If the user's body had 5 visible references and 25 lived in footnotes,
the LaTeX output would contain exactly 5 — matching the reported "only
converts 5 references" symptom exactly.

### The fix

`convert_docx_to_latex` now reads all three OOXML parts
(`word/document.xml`, `word/footnotes.xml`, `word/endnotes.xml`) using a
single shared zip archive, and parses each with the same `parse_blocks`
walker. Footnote and endnote blocks are appended to the end of the body
under injected `\section*{Footnotes}` and `\section*{Endnotes}` headings
so the user can see where each part of the source document landed in the
LaTeX output. A per-part warning is recorded:

> `N footnote paragraph(s) were extracted from word/footnotes.xml and
> appended under a "Footnotes" section. Verify against the source
> document.`

The injected section headings are deliberately unnumbered
(`\section*{}` instead of `\section{}`) and are not counted in the
`headings` field of `DocxToLatexResult`, so the UI counter on the result
card still reflects source headings only.

### Verification

Five new Rust regression tests in `src-tauri/src/docx_to_latex.rs`:

1. `converts_all_plain_paragraph_references` — 10 plain-paragraph
   references (no footnotes). Locks in that there is no hidden cap on
   body references; the previous AI's `.take(5)` hypothesis would have
   failed this test if it had ever existed.
2. `converts_all_numbered_list_references` — 12 numbered-list references
   using the realistic `<w:ilvl>` + `<w:numId>` children MS Word
   actually emits (not the `<w:numPr/>` self-closing shorthand in the
   existing fixture). All 12 are collected into a single `itemize`
   environment.
3. `extracts_footnote_references_not_just_document_xml` — 5 body refs
   + 15 footnote refs. Asserts all 20 appear in the output, the
   `\section*{Footnotes}` heading is injected, and the warning is
   recorded. This is the test that would have failed before the fix and
   is the direct regression guard for the user's bug report.
4. `extracts_endnote_references` — 3 body refs + 8 endnote refs. Same
   property for the endnotes path.
5. `no_warnings_when_docx_has_no_footnotes_or_endnotes` — 4 plain
   references, no footnotes/endnotes parts. Guards the no-op path so a
   .docx without those parts produces no spurious section headings or
   warnings.

All 5 tests pass against a verbatim copy of the `parse_blocks` /
`render` / `read_zip_part` logic in an isolated Rust harness using the
same `quick-xml` 0.31 and `zip` 8.6 crates the project depends on. The
full project test suite (`cargo test --lib docx_to_latex`) will run them
natively on the maintainer's machine.

### UI copy update

`AITextCleaner.svelte`'s result card previously said "Images, equations,
footnotes, and text boxes are not converted". The "footnotes" item was
no longer accurate after this fix; the copy now reads:

> Images, equations, and text boxes are not converted; footnote and
> endnote paragraphs (common in Chicago notes-bibliography and
> Vancouver-style manuscripts) are extracted from word/footnotes.xml
> and word/endnotes.xml and appended under `\section*{Footnotes}` /
> `\section*{Endnotes}` headings.

## Headline 2: Professional button shadows + refined heading alignment

The user reported that "buttons are not quite visible to the user" and
asked for "professional shadow around all buttons in all pages of the
app", plus an adjustment of "text alignment under the heading of all
pages properly and professionally". Both are scoped strictly to:

- `public/app.css` — the base `button` selector and `.primary` /
  `.danger` variants.
- `src/components/PageHeader.svelte` — the `.lead` subtitle paragraph
  that sits under each page's `<h1>`.

No other UI elements are touched.

### Button shadows

The base `button` rule previously had no `box-shadow` at all, so
non-primary buttons blended into the page background. Only `.primary`
had a subtle `0 1px 2px rgba(16,24,40,0.12)` shadow, and `.danger` had
none, producing inconsistent tactile depth across the three button
variants.

The new design applies a uniform "subtle elevation" shadow to every
button via the base selector — a two-layer composite:

```css
box-shadow:
  0 1px 2px rgba(16, 24, 40, 0.08),   /* tight contact shadow */
  0 1px 1px rgba(16, 24, 40, 0.04);  /* slightly wider ambient */
```

On hover the shadow lifts to a `0 2px 6px rgba(16,24,40,0.16)` composite
for interactive feedback; the existing `box-shadow` transition (already
in the `button` rule) makes the lift read as a soft motion rather than
a snap. Disabled buttons drop the shadow entirely (`box-shadow: none`)
so they read as inert and pressed-flat, not floating.

The previous hard-coded `.primary` `box-shadow` was removed in favor of
the inherited base shadow, so all three variants (regular / .primary /
.danger) now share the same depth. The visual change for `.primary` is
negligible (the new shadow is nearly identical in opacity to the old
one) but the change for regular and `.danger` buttons is the substantive
fix.

### Heading lead alignment

`PageHeader.svelte`'s `.lead` paragraph under each page's `<h1>` was a
bare left-aligned paragraph with no line-height or width guidance, so
long descriptions sprawled edge-to-edge and read as a wall of text.

The `.lead` now uses a refined left-align:

```css
max-width: 720px;          /* 45-80 character readability band */
line-height: 1.55;         /* opens up the leading so the eye can track */
color: var(--text-muted);  /* de-emphasizes relative to the h1 */
letter-spacing: 0.01em;    /* quiet, academic feel */
text-align: left;          /* explicit so future overrides don't inherit */
```

Applied consistently to every page that uses the `PageHeader` component,
which is all of them. Card subtitles (`.card .card-subtitle`) are not
touched — only the page-level lead.
